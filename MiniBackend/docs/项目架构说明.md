# MiniBackend 项目架构说明

> 本文档帮助你从"整体框架"的视角理解这个项目：每个文件负责什么、层与层之间如何调用、一次 HTTP 请求从进入到返回的全过程。

---

## 1. 项目是什么

这是一个**用 C++ 从零手写的迷你 HTTP 后端服务**（MiniBackend），监听 8080 端口，提供两个接口：

| 方法 | 路径 | 功能 |
|------|------|------|
| POST | `/user` | 创建一个用户（从请求 JSON body 读取 name 和 age） |
| GET | `/user/:id` | 根据 id 查询用户（`:id` 是路径参数） |

数据目前存在**内存**里（进程退出数据就没了），没有接数据库。

启动方式：

```bash
cd MiniBackend
mkdir build && cd build
cmake .. && make
./minibackend
# 测试
curl -X POST localhost:8080/user -d '{"name":"Tom","age":18}'
curl localhost:8080/user/1
```

## 2. 技术栈

| 项目 | 说明 |
|------|------|
| 语言/标准 | C++17 |
| 网络 | 系统调用 `socket / bind / listen / accept / recv / send`（Linux/macOS） |
| JSON | 第三方库 nlohmann/json |

| 线程模型 | 单线程、阻塞式、一次只能处理一个请求 |

## 3. 整体架构：分层图

```
┌─────────────────────────────────────────────────────────────┐
│                     客户端 (curl / 浏览器 / 前端)             │
└──────────────────────────┬──────────────────────────────────┘
                           │ 原始字节流 (HTTP 报文文本)
┌──────────────────────────▼──────────────────────────────────┐
│ ① 网络层  src/server/Server.cpp                             │
│    socket 监听 → 接受连接 → 读字节 → 交给上层 → 写回字节     │
├─────────────────────────────────────────────────────────────┤
│ ② HTTP 协议层  src/http/                                    │
│    Http::parseRequest : 字节流 → Request 结构化对象          │
│    Response::serialize : Response 对象 → 字节流              │
├─────────────────────────────────────────────────────────────┤
│ ③ 路由层  src/router/Router.cpp                             │
│    URL + 方法 → 匹配到对应的处理函数 (Handler)               │
├─────────────────────────────────────────────────────────────┤
│ ④ 控制层  src/controller/UserController.cpp                 │
│    解析请求参数 → 调用业务层 → 组装 Response                 │
├─────────────────────────────────────────────────────────────┤
│ ⑤ 业务层  src/service/UserService.cpp                       │
│    业务规则（比如 id 自动递增）                              │
├─────────────────────────────────────────────────────────────┤
│ ⑥ 数据层  src/repository/UserRepository.cpp                 │
│    真正存取数据（目前是内存 vector，以后可换成数据库）       │
├─────────────────────────────────────────────────────────────┤
│ ⑦ 模型层  src/model/User.h                                  │
│    纯数据结构，不包含任何逻辑                                │
└─────────────────────────────────────────────────────────────┘
```

核心思想：**每一层只负责一件事**，并且**只依赖它下面那一层**，不能反向依赖。

## 4. 一次请求的完整旅程（最重要，建议反复读）

以 `GET /user/1` 为例：

```
1. 客户端通过 TCP 连接发来一段文本：
   "GET /user/1 HTTP/1.1\r\nHost: localhost:8080\r\n\r\n"

2. Server::acceptLoop() 用 accept() 拿到客户端连接
   └─ readRequest() 用 recv() 读出原始字节流

3. Http::parseRequest(字节流) 解析出 Request 对象：
   method="GET"  path="/user/1"  headers={...}

4. Router::handle(Request) 逐个匹配注册过的路由：
   GET /user/:id 命中 → 把 "1" 填进 request.params["id"]
   → 调用绑定的处理函数 UserController::getUserById

5. UserController::getUserById 从 params 取出 id=1
   → 调用 UserService::getUserById(1)
   → UserService 调用 UserRepository::findById(1)
   → Repository 在内存 vector 里线性查找，返回 User*

6. 结果逐层返回：
   Controller 把 User 转成 JSON 文本
   → Response::json(...) 生成 200 OK 的 Response 对象

7. Response::serialize() 把对象序列化成 HTTP 报文文本

8. Server 用 sendAll() 写回客户端，close() 关闭连接
```

创建用户的流程（POST /user）与之类似，只是多了一步：

```
Request.body 里有 JSON 文本 {"name":"Tom","age":18}
→ Controller 用 nlohmann::json 解析出 name、age
→ Service 给用户分配自增 id，调用 Repository::save 存入内存
→ 返回带 id 的完整用户 JSON
```

## 5. 逐文件详解

### 5.0 CMakeLists.txt — 构建配置

把哪些 `.cpp` 编译成一个可执行文件 `minibackend`，依赖 `nlohmann_json` 库，启用 `-Wall -Wextra` 警告。**每新增一个 `.cpp` 文件都要在这里登记**（注意：目前第 32 行写的是 `src/repository/UserRepository`，**漏了 `.cpp` 后缀**，但能编译通过是 CMake 的容错行为，建议补上）。

### 5.1 src/main.cpp — 程序入口

```cpp
Server server(8080);
server.start();
```

只有 8 行：创建 Server 并启动。项目从这里开始执行。

### 5.2 src/model/User.h — 数据模型层

```cpp
struct User {
    int id;
    std::string name;
    int age;
};
```

纯粹的"数据结构"，只有字段、没有任何行为。它是所有层之间传递数据的载体，被 Repository/Service/Controller 共同使用。

### 5.3 src/http/ — HTTP 协议层

这一层负责"原始字节流 ↔ 结构化对象"的转换，是浏览器/前端和你的业务代码之间的翻译官。

| 文件 | 职责 |
|------|------|
| `Request.h` | 请求的数据结构：method、path、version、headers、body、params（路由参数） |
| `Http.h/.cpp` | 静态方法 `parseRequest`：把 HTTP 报文文本解析成 `Request` 对象（解析请求行 + 头部 + body） |
| `Response.h` | 响应的数据结构：statusCode、statusText、headers、body |
| `Response.cpp` | ① `serialize()`：把 Response 对象拼成 HTTP 报文文本；② `json()`：快速生成 200 JSON 响应；③ `error()`：快速生成错误响应（400/404） |

这一层的代码**不关心业务**，只关心 HTTP 协议本身。

### 5.4 src/router/Router.cpp — 路由层

"**URL 分发器**"：把 `方法 + 路径` 映射到处理函数。

- `get() / post()`：注册路由，比如 `router_.get("/user/:id", handler)`
- `match()`：做路径匹配，`:id` 这种 `冒号开头` 的段是**路径参数**，匹配时把实际值写入 `request.params`
- `handle()`：遍历所有注册的路由，找到第一个命中的就调用它的 handler；一个都没命中就返回 404

所有业务逻辑对 Router 来说只是 `std::function<Response(const Request&)>` 这样一个函数签名，Router 不关心 handler 内部是什么。

### 5.5 src/controller/UserController.cpp — 控制层

"**接口的接线员**"：一个接口对应一个 Controller 方法，负责：

1. 从 Request 里取出参数（路径参数、JSON body）
2. 调用 Service 层做业务处理
3. 把结果组装成 Response（成功 → `Response::json`，失败 → `Response::error`）

注意：Controller **不做业务判断**（比如"id 怎么生成"不归它管），它只做参数解析和结果包装。它持有 `UserService&` 引用，通过构造注入。

### 5.6 src/service/UserService.cpp — 业务逻辑层

"**业务规则所在地**"：

- `createUser`：生成自增 id（`static int count` 全局计数器），创建 User 并交给 Repository 保存
- `getUserById`：直接转交给 Repository 查询

在真实项目里，这一层会承载更复杂的业务：比如"创建用户前检查名字是否重复""未成年不能注册"等等。目前因为项目小，这一层看起来像"透传"，但它是一个承上启下的关键分层——将来加规则时不用改 Controller 和 Repository。

### 5.7 src/repository/UserRepository.cpp — 数据访问层

"**数据存储和读取**"：

- `save()`：把用户追加进内存的 `std::vector<User>`
- `findById()`：遍历 vector 按 id 查找，找到返回指针，找不到返回 `nullptr`

将来接真正的数据库（MySQL 等）时，**只需要改这一层**，上面的 Service/Controller 完全不用动——这就是分层的好处。

### 5.8 src/server/Server.cpp — 网络服务层

项目的"**大管家**"（composition root，组装根）：

- **系统调用部分**：`createSocket → bindSocket → listenSocket → acceptLoop`，完成 TCP 监听、接受连接、读请求字节、写响应字节
- **组装部分**：构造函数里创建 `UserService`、`UserController`、`Router`，并注册路由（把 Controller 的方法绑定到 URL 上）
- `readRequest()`：因为一次 `recv()` 不一定能收全整个请求，所以要循环读；先读到 `\r\n\r\n` 表示头部结束，再按 `Content-Length` 读满 body

`Server.h` 里的成员变量就是"整个项目组装了哪些部件"的清单：

```cpp
Router router_;            // 路由表
UserService userService_;  // 业务层
UserController userController_;  // 控制层
```

## 6. 模块依赖关系

```
main.cpp
   └─ Server ──────────────┬─ Router ──────┬─ Request / Response
                           │               │
                           ├─ UserController ──┬─ UserService ──┬─ UserRepository ──┬─ User (model)
                           │                   │                │
                           └─ Http (解析用)    └─ nlohmann::json
```

关键规则：

- **依赖方向是单向的**：main → Server → (Router, Controller) → Service → Repository → Model
- **Controller 不直接碰数据**：数据访问必须经过 Service → Repository
- **Repository 不知道 Controller 的存在**：低层对上层一无所知
- 如果画一条"知识流动"线：越往下越接近"数据/系统"，越往上越接近"用户请求"

## 7. 为什么这样分层？（设计意图）

| 层 | 一句话职责 | 换掉/修改它不影响谁 |
|----|-----------|---------------------|
| HTTP 协议层 | 字节 ↔ 对象 | 换成别的 HTTP 库，业务代码不用动 |
| 路由层 | URL → 函数 | 换路由规则，Controller 不用动 |
| Controller | 参数解析 + 结果包装 | 改接口返回格式，Service 不用动 |
| Service | 业务规则 | 加业务逻辑，其他层不用动 |
| Repository | 数据存取 | 换成真数据库，Service 不用动 |
| Model | 数据载体 | 所有层都可能受影响（所以要定义得最稳定） |

对你未来学习的意义：**真实公司的后端项目（Java Spring、Go、Python Django 等）也是同样的分层思想**，只是换成了对应语言的框架。理解了这里的每一层，再看任何 Web 框架都会觉得眼熟。

## 8. 和"真实前后端项目"的差距（未来扩展方向）

你现在这个项目等于"后端的一半"，真实的完整项目还包括：

1. **前端**：浏览器里的页面用 `fetch / axios` 发 HTTP 请求到你的接口，你返回的 JSON 就是前端渲染的数据来源。你现在用 curl 测试，就是扮演了前端的角色。
2. **数据库**：Repository 层换成 MySQL/SQLite，数据持久化。
3. **并发**：现在单线程串行处理请求，一个请求卡住所有请求都排队。真实项目会改成多线程/线程池/异步。
4. **更完整的 HTTP 支持**：现在是简化版，真实场景建议直接上成熟 HTTP 框架（C++ 有 Crow、Drogon，或直接用 Nginx + FastCGI）。
5. **JSON 解析容错**：现在 `createUser` 直接 `json::parse(request.body)`，body 不是合法 JSON 会直接抛异常导致进程崩溃，真实项目会 try-catch 并返回 400。
6. **指针隐患**：`UserRepository::findById` 返回指向 vector 内部元素的指针，vector 扩容时指针会失效（悬垂指针），真实项目更常用值拷贝、智能指针或数据库主键。
7. **日志、配置、测试、部署**：真实项目的标配，这里都还没有。

## 9. 快速记忆清单

```
加一个"查询用户列表"接口，需要动哪些文件？
1. UserRepository  加 list() 方法（数据层）
2. UserService     加 listUsers()（业务层）
3. UserController  加 listUsers() 方法（控制层）
4. Server.cpp 构造函数里 router_.get("/users", ...) 注册路由（组装）
5. CMakeLists.txt  一般不用动（除非加了新文件）
```

从上往下加代码，从下往上选数据结构——这就是分层开发的节奏。
